1. Overview & Payment Architecture

IEMA.ai uses three independent, parallel payment paths that all converge on the same backend crediting logic. No single provider is used everywhere — each is scoped to what platform policy requires or what best fits the checkout surface.

SurfaceRecurring plans (subscriptions)One-time top-up packs
iOS appiOS Apple StoreKit 2 (via expo-iap)Razorpay Payment Links (in-app browser)
Android appAndroid Google Play Billing (via expo-iap)Razorpay Payment Links (in-app browser)
Web appRazorpay SubscriptionsRazorpay Payment Links (hosted checkout)

Recurring plans on mobile must use native store billing — this is required by both Apple App Store Review Guideline 3.1.1 and Google Play's Billing policy for unlocking in-app digital content. Top-up packs are permitted to use Razorpay because they map to a real, off-platform account credit balance rather than unlocking in-app content directly.

RevenueCat sits on top of the native store billing as an observer, not a competing checkout. The app's own purchase flow (via expo-iap) still owns the actual checkout and server-side receipt verification; RevenueCat is configured with purchasesAreCompletedBy: MY_APP so it only watches StoreKit/Play Billing transactions and mirrors entitlement state — it does not take over payment and does not affect the existing verify/credit flow.

Why RevenueCat at all, if the app already verifies receipts itself?
It gives a single dashboard across both stores for subscription analytics or ended up being requested for future flexibility (e.g. cross-platform entitlement checks, churn/retention reporting) without having to build that tooling from the two different store APIs directly.

2. Backend Payment Module Map

All payment logic funnels through IEMA_AI_API_V3/services/payments_service.py and is exposed via IEMA_AI_API_V3/routers/payments_routes.py. Three independent payment paths converge on the same two helper functions:

FunctionPurpose
_credit_planShared success handler — assigns the plan and upserts the subscriptions document. Called by all three providers.
_revoke_planDowngrades a user to the free plan on cancellation/expiration.
get_or_create_rzp_planCreates/reuses an immutable Razorpay Plan at the current price (INR-only).
create_subscriptionCreates a Razorpay Subscription for a user + plan (web only).
handle_razorpay_webhookVerifies signature; processes subscription.charged / activated / cancelled events.
verify_apple_receiptVerifies an Apple receipt against verifyReceipt (prod, falling back to sandbox on status 21007). Idempotent on transaction_id.
verify_google_receiptVerifies a Google Play purchase/subscription token via the Android Publisher API (service-account auth). Idempotent on purchase_token.
handle_revenuecat_webhookAuth-checked RevenueCat observer webhook — grants on INITIAL_PURCHASE / RENEWAL / PRODUCT_CHANGE / UNCANCELLATION, revokes on CANCELLATION / EXPIRATION.

Routes

POST /payments/razorpay/order              # one-time top-up (web + mobile)
GET  /payments/razorpay/link-status/{id}   # poll payment-link status
POST /payments/razorpay/verify             # signature-verify path
POST /payments/subscribe/{plan_id}         # create Razorpay subscription (web)
POST /payments/webhook/razorpay-subscription
POST /payments/iap/apple/verify            # iOS receipt verify → credit plan
POST /payments/iap/google/verify           # Android purchase verify → credit plan
POST /payments/webhook/revenuecat          # RevenueCat observer webhook (hidden from schema)

No Stripe or PayPal integration exists. Stripe was explicitly removed per a prior product decision ("all web payments go through Razorpay") — a few dead code fragments referencing it remain (a legacy PaymentTransaction.provider schema literal, an unreachable PaymentSuccess.jsx polling branch) but there is no live Stripe code path.

3.2 Code: enabling Android observer mode

supercreater-ai-frontend/mobile/src/services/revenuecat.js previously hard-gated on Platform.OS !== 'ios', meaning Android never configured RevenueCat at all. This was relaxed to configure on both platforms, selecting the correct SDK key per platform:

const REVENUECAT_API_KEY = Platform.select({
  ios: Constants.expoConfig?.extra?.revenueCatIosKey,
  android: Constants.expoConfig?.extra?.revenueCatAndroidKey,
});

export function initRevenueCat(userId) {
  if (_configured || !userId || !REVENUECAT_API_KEY) return;
  const Purchases = loadPurchases();
  if (!Purchases) return;

  const { PURCHASES_ARE_COMPLETED_BY_TYPE, STOREKIT_VERSION } = require('react-native-purchases');
  Purchases.configure({
    apiKey: REVENUECAT_API_KEY,
    appUserID: userId,
    purchasesAreCompletedBy: {
      type: PURCHASES_ARE_COMPLETED_BY_TYPE.MY_APP,
      storeKitVersion: STOREKIT_VERSION.STOREKIT_2,
    },
  });
  _configured = true;
}

storeKitVersion is an iOS-only field that Android silently ignores, so the same purchasesAreCompletedBy configuration object is safely shared across both platforms without branching.

3.3 Moving API keys out of source

The iOS key had previously been hardcoded directly in revenuecat.js. Both keys were moved to environment variables, which required converting the static app.json to a dynamic app.config.js (needed to read process.env at config-evaluation time):

// app.config.js
extra: {
  apiBaseUrl: "https://api.iema.ai",
  revenueCatIosKey: process.env.REVENUECAT_IOS_API_KEY,
  revenueCatAndroidKey: process.env.REVENUECAT_ANDROID_API_KEY,
  eas: { projectId: "d6e0dba8-f63e-40a4-8cba-baa765a2f423" }
}

A local .env (gitignored) and a committed .env.example were added for local development. For EAS Cloud builds, both variables were also registered directly as EAS project environment variables (via eas env:create) across the production, preview, and development environments, so cloud builds pick them up automatically without needing the local .env file.

This was used repeatedly during this project to catch a device silently running the public Production release (build 30) instead of the intended Internal Testing build, even after using the official opt-in link — caused by testing-track propagation/serving delay on Google's side. 4.3 Release process used throughout

  1. eas build --platform android --profile production — builds the .aab.
  2. Download the .aab from the EAS build artifact URL (files were routinely 55–60 MB, too large for direct browser-automation upload — always downloaded and uploaded manually via the Play Console UI).
  3. Play Console → Test and release → Internal testing → Releases → Create new release → attach the bundle (via "Add from library" once uploaded) → resolve the (harmless, recurring) "no deobfuscation file" warning → Save and publish.

7. Root-Cause Bugs Found & Fixed

This was the most significant finding of the whole project. Every single "Product not found" test failure — on both platforms, across many rounds of Play Console pricing/country/tester fixes — turned out to have nothing to do with store configuration. The expo-iap dependency had been upgraded to ~3.0.0, which ships a completely rewritten "unified" API, and the app's iap.js was never updated to match. Three distinct API-shape mismatches were silently throwing and being swallowed by broad try/catch blocks, which is why every failure looked identical ("Product not found") regardless of the actual cause.

7.1 getSubscriptions no longer exists Both platforms

Bug: loadSubscriptions() called iap.getSubscriptions({ skus: SUB_PRODUCT_IDS }). This method does not exist on expo-iap@~3.0.0 — it throws TypeError: undefined is not a function, caught by an empty catch { return [] }, so the app always believed the store returned zero products.
Fix: replaced with the new unified query: 
_subscriptions = (await iap.fetchProducts({ skus: SUB_PRODUCT_IDS, type: 'subs' })) || [];
(The || [] guards against the documented null return case.)

7.2 Android offer-token field renamed Android

Bug: the base-plan offer lookup used the old field name product?.subscriptionOfferDetails?.[0]?.offerToken. In the new API this field is subscriptionOfferDetailsAndroid. Additionally, requestPurchase's type: 'subs' variant now requires a top-level willAutoRenew: boolean field that wasn't being sent.
Fix: 
const offerToken = product?.subscriptionOfferDetailsAndroid?.[0]?.offerToken;
return iap.requestPurchase({
  request: { android: { skus: [sku], ...(offerToken ? { subscriptionOffers: [{ offerToken }] } : {}) } },
  type: 'subs',
  willAutoRenew: true,
});

7.3 Stale productId field check in the UI Both platforms

Bug: Product/ProductSubscription objects in the new API use an id field for the SKU, not productId (that name is reserved for Purchase objects, which are a different type and unaffected). BillingScreen.js's availability check iapProducts.some((p) => p.productId === sku) could never match, even once fetchProducts was fixed.
Fix: iapProducts.some((p) => p.id === sku || p.productId === sku) (checks both, defensively).

7.4 iOS receipt format changed iOS

Bug: verifyPurchase()'s iOS branch read purchase?.jwsRepresentation || purchase?.transactionReceipt — both fields have been removed from the Purchase type in the new API, unified into a single purchaseToken field (which on iOS carries the StoreKit 2 JWS representation). Sending that JWS token to the backend's Apple verifyReceipt endpoint would not have worked either way — that legacy Apple endpoint expects the classic base64 receipt blob, a different format entirely from a StoreKit 2 JWS.
Fix: rather than reading anything off the purchase object, the classic receipt is now fetched directly via a dedicated query the library still exposes for this exact purpose: 
const iap = loadIap();
const receipt = await iap?.getReceiptDataIOS?.();
if (!receipt) return { ok: false, error: 'no iOS receipt' };
const { data } = await api.post('/payments/iap/apple/verify', { receipt });
This required no backend changes — the backend's legacy-format expectation is satisfied without migrating to Apple's newer JWS-based App Store Server API.

8. The Apple W-9 Tax ID Conflict

Independent of the code bugs above, iOS testing was blocked for a period by an Apple-side account issue: submitting a U.S. Form W-9 for IEM AMERICA CORPORATION under Business → Agreements, Tax, and Banking failed with:

"The Tax ID entered already exists."

This is a backend Apple conflict (a duplicate EIN record somewhere in Apple's systems), not fixable from the App Store Connect UI. It was escalated via Contact Us About Financial Information (Category: Tax information submissions) at developer.apple.com/contact/finance/, referencing the exact error, the account, and confirming no other Apple Developer account exists for this entity/EIN. Apple resolved it; the W-9 was later resubmitted successfully, unblocking product resolution on the App Store side.

9.2 eas.json submit configuration added

"submit": {
  "production": {
    "android": { "track": "internal" },
    "ios": { "ascAppId": "6755818728" }
  }
}

Before this was added, eas submit for both platforms failed non-interactively with a credentials-setup prompt it couldn't resolve unattended ("Google Service Account Keys cannot be set up in --non-interactive mode" / "Set ascAppId in the submit profile"). Adding the explicit config values fixed both.

9.3 A build-environment pitfall: expo-doctor

A one-off expo-doctor dev-dependency install (added purely for local diagnostics) broke the very next EAS Android build: expo-doctor@1.20.1 requires Node ^20.19.4, but the EAS build worker image runs Node 20.19.2 — just under the minimum — which failed the whole yarn install --frozen-lockfile step.
Removed via yarn remove expo-doctor. Lesson: dev tools added for local-only diagnostics should be run via npx rather than persisted to package.json if there's any chance their engine requirements diverge from the CI/build image.

Separately, a stray package-lock.json (this project is yarn-managed per its README/LAUNCH_GUIDE) was found committed alongside yarn.lock from an earlier, unrelated npm install. It was removed to prevent a repeat of an incident during this project where running npm install locally silently rewrote yarn.lock.

10. Testing & Verification Journey

A condensed timeline of the debugging path, since the same symptom ("Product not found") had several unrelated causes layered on top of each other:

  1. iOS, first attempt: "Product not found" for all 4 products → traced to the Apple W-9 tax form being incomplete (§8) → escalated to Apple Support.
  2. Android, first attempt (build 32): same error → traced to all 4 Play Console base plans being India-only → expanded to 177 countries (§4.1).
  3. Android, second attempt: same error again, even after the pricing fix and a long wait for propagation, and after clearing the Play Store app's cache/data → real root cause was the expo-iap API mismatch (§7), confirmed by adding temporary console.log instrumentation and reading it live via adb logcat.
  4. A version-tracking detour: partway through, the test device was found to be silently running the public Production build (versionCode 30) instead of the intended Internal Testing build, despite using the correct opt-in link — versionName alone couldn't reveal this; adb shell dumpsys package was needed to confirm the real installed versionCode each time before trusting a test result.
  5. Android, after the real fix (build 35): logs showed com.android.billingclient.api.ProxyBillingActivity actually launching — the genuine Google Play purchase confirmation screen — confirming fetchProducts and requestPurchase now worked end-to-end. RevenueCat's observer picked up the billing event in real time.
  6. iOS, after Apple cleared the W-9 and the same code fix shipped (build 56): subscription purchase completed successfully.
